3.1.2 Fase de diseño

Objetivo. Definir una solución centrada en el usuario que alineara los flujos operativos del área de facturación con la arquitectura técnica requerida para consumir la API MIPRES.

Justificación. La clínica necesitaba una interfaz comprensible para personal administrativo y, al mismo tiempo, una capa técnica capaz de preservar seguridad, trazabilidad y cumplimiento normativo; el diseño resolvió esa dualidad antes de pasar a desarrollo.

Actividades desarrolladas.

  • Se levantó la caracterización de actores, escenarios y criterios de aceptación mediante entrevistas y talleres, consolidando un mapa de experiencia que prioriza los puntos de dolor (Ver Anexo D).
  • Se modeló la arquitectura de información, la jerarquía de navegación y las interacciones entre frontend React, backend NestJS y servicios MIPRES, definiendo diagramas de componentes y secuencia que delimitan responsabilidades (Ver Anexo F).
  • Se documentó el sistema de diseño con paleta cromática, tipografías, estados de botones y mensajes guía, además del inventario de campos y catálogos necesarios para cada formulario (Ver Anexo E y Ver Anexo B).

3.1.3 Fase de desarrollo

Objetivo. Construir el ecosistema web (frontend y backend) que automatiza el reporte y envío hacia la plataforma MIPRES de forma segura, trazable y mantenible.

Justificación. La materialización temprana de prototipos en código permitió validar requerimientos, reducir deuda técnica y garantizar que cada iteración quedara respaldada por pruebas y control de versiones.

Actividades desarrolladas.

  • Se configuraron repositorios independientes para NestJS y React, scripts de linting y convenciones de ramas, asegurando integridad en cada commit y facilitando despliegues controlados (Ver Anexo F).
  • Se implementó el backend en NestJS integrando módulos Auth y Mipres, tuberías de validación (ValidationPipe), límites de peticiones (ThrottlerModule), normalización de cabeceras y manejo robusto de errores antes de invocar los servicios oficiales.
  • Se desarrolló el frontend en React/Vite con componentes reutilizables (ToastStack, ResponsePanel, StatCard), formularios controlados, persistencia en localStorage y descarga automática del reporte JSON diario.
  • Se ejecutaron pruebas unitarias e integraciones manuales con colecciones de Postman y datos anonimizados de la clínica, cerrando cada sprint con revisión conjunta y minutas de hallazgos (Ver Anexo H).

3.1.4 Fase de implementación

Objetivo. Integrar localmente todos los componentes (frontend, backend y servicios MIPRES) y validar que los flujos operativos funcionen de extremo a extremo antes de solicitar despliegues en la infraestructura de la clínica.

Justificación. Mantener las pruebas en un entorno local controlado permitió iterar con rapidez, minimizar riesgos sobre la infraestructura institucional y generar evidencia previa que respalde la solicitud formal de publicación en los servidores corporativos, cuya aprobación depende del Ingeniero Senior.

Actividades desarrolladas.

  • Se configuró el entorno de trabajo ejecutando npm run dev para el frontend y npm start para el backend, gestionando variables sensibles mediante archivos .env resguardados y verificados junto con el ingeniero de soporte que supervisó cada iteración.
  • Se validó la integración con la API MIPRES consumiendo los endpoints reales: generación de token, envío de entregas y facturación con facturas de bajo valor. Cada operación se contrastó en el Swagger oficial para confirmar que los registros quedaran cargados con los parámetros exigidos y que las respuestas HTTP se interpretaran correctamente.
  • Se documentó el procedimiento de ejecución local, los prerequisitos técnicos y la ruta de escalamiento para solicitar autorización de despliegue al Ingeniero Senior. Este material servirá como base del futuro playbook de instalación una vez se apruebe el traslado a servidores de la clínica (Ver Anexo G).

El proyecto propone la conexión a la base de datos institucional para extraer CUFE, CUM y códigos EPS. Dicha integración solo se realizará con autorización explícita del Ingeniero Senior; en caso de no contar con los permisos, la aplicación continuará operando con los catálogos locales preparados durante esta fase.

3.1.5 Fase de evaluación

Objetivo. Medir el desempeño funcional y la aceptación del sistema frente a los indicadores definidos de tiempo, calidad y satisfacción del usuario.

Justificación. La evaluación conjunta con el personal de facturación permitió comparar el uso de la interfaz gráfica frente al flujo tradicional en Swagger, cuantificar los ahorros de tiempo y evidenciar ajustes necesarios antes de solicitar el despliegue institucional.

Actividades desarrolladas.

  • Se definieron indicadores (tiempo de diligenciamiento, número de correcciones, devoluciones y percepción de claridad) y se prepararon bitácoras y cronómetros de seguimiento para capturar los datos durante las sesiones (Ver Anexo D).
  • Se realizaron sesiones guiadas con el facturador líder y cuatro auxiliares, ejecutando cargas de prueba en la interfaz gráfica y en Swagger, midiendo el tiempo en cada paso y registrando observaciones y errores detectados.
  • Se consolidaron los resultados en tableros comparativos, se analizaron las causas raíz de las incidencias y se emitió el informe final con recomendaciones priorizadas para la siguiente iteración (Ver Anexo H).

3.2 Instrumento de medición y recolección de datos

Se utilizaron cuatro instrumentos complementarios: una matriz de levantamiento que recoge actor, tarea, puntos de control, campos requeridos y riesgos operativos por operación MIPRES; bitácoras digitales en Excel/Sheets donde cada envío registra fecha, usuario, tiempo de diligenciamiento, estado HTTP, observaciones y acciones correctivas; encuestas de satisfacción con escala Likert aplicadas al cierre de cada iteración para valorar facilidad, claridad, confianza y soporte; y registros automáticos generados por el backend NestJS con información detallada de cada solicitud. La triangulación de estos instrumentos permitió cruzar percepciones de los usuarios con evidencia objetiva y trazable (Ver Anexo D y Ver Anexo H).

3.3 Muestra y población del proyecto

La población objetivo estuvo conformada por 12 colaboradores del Departamento de Facturación de la Clínica San José de Cúcuta (coordinador, siete auxiliares, tres analistas de cartera y un profesional de auditoría). La muestra piloto se seleccionó de manera intencional con cinco participantes que concentraban el 68 % del volumen de envíos MIPRES y contaban con disponibilidad para sesiones de co-diseño y validación. Se equilibraron perfiles por experiencia y turnos para capturar variaciones de uso. El equipo recibió una sesión de inducción de 90 minutos y acompañamiento remoto durante la primera semana operativa.

3.3.1 Análisis de datos

El análisis combinó técnicas cuantitativas y cualitativas. Se realizó estadística descriptiva sobre tiempos de proceso, errores y devoluciones pre y post implementación; se aplicó un test t pareado para validar la reducción de tiempos (p < 0,05); se agruparon incidencias por categoría contrastando bitácoras y logs; y se codificaron las respuestas abiertas de las encuestas para identificar patrones de satisfacción o fricción. Los hallazgos se sintetizaron en tableros comparativos y en narrativas de casos ilustrativos que respaldan las conclusiones operativas (Ver Anexo H).

4 Resultados

Los resultados se organizan según los tres objetivos específicos definidos al inicio del proyecto. Para el Objetivo 1 (analizar el proceso actual) se obtuvieron insumos que evidencian los puntos críticos y las dependencias con el área de sistemas. El Objetivo 2 (diseñar una interfaz guiada) concluyó con una propuesta de experiencia paso a paso validada por los usuarios. El Objetivo 3 (implementar la lógica de transformación y las integraciones) entregó la plataforma funcional que automatiza la generación de JSON conforme a MIPRES y devuelve respuestas auditables. Los apartados siguientes sintetizan los hallazgos y entregables alcanzados en cada objetivo.

4.1 Objetivo específico 1: Analizar el proceso actual de reporte y envío a MIPRES

El diagnóstico integral del flujo permitió identificar cuellos de botella, dependencias con el área de sistemas y riesgos de cumplimiento que antes no estaban visibilizados. Esta línea base sustentó los criterios de diseño y los indicadores de evaluación.

4.1.1 Actividad 1. Levantamiento del proceso actual

Se realizaron sesiones de trabajo con cinco colaboradores del equipo de facturación para repasar, paso a paso, el manual que ya empleaban al diligenciar el formulario de Swagger. Durante las jornadas se documentaron cada campo, los puntos donde debían acudir a sistemas para solicitar CUFE, CUM o código EPS (presencialmente o por correo) y los reprocesos asociados. Con esa información se construyó una secuencia detallada del flujo actual y sus dependencias (Ver Anexo A).

4.1.2 Actividad 2. Inventario de datos y catálogos

Se estructuró una hoja de cálculo (formato XLSX) con todos los datos solicitados por MIPRES, indicando origen, formato y responsable de actualización. Sistemas mantiene la custodia de CUM, CUFE y códigos EPS, mientras que facturación alimenta información operativa como número de prescripción, identificación del paciente, valores unitarios y totales. Este inventario alimenta los catálogos locales y servirá para habilitar autocompletados cuando se autorice la conexión a la base institucional (Ver Anexo B).

4.1.3 Actividad 3. Identificación de riesgos y brechas

Se construyó una matriz de riesgos con seis amenazas agrupadas en dimensiones operativa, tecnológica y normativa. Para cada riesgo se estimó probabilidad, impacto y plan de mitigación. Los escenarios críticos identificados fueron el mal diligenciamiento de valores unitarios y totales, inconsistencias en el JSON enviado al servicio externo y la indisponibilidad del soporte de sistemas para suministrar datos sensibles, además de riesgos asociados a caducidad de tokens, fallos de red y pérdida de evidencias (Ver Anexo C).

Esta caracterización integral del proceso actual permitió cumplir el Objetivo específico 1.

4.2 Objetivo específico 2: Diseñar la interfaz web para el equipo de facturación

El diseño centrado en el usuario entregó una interfaz escalable, accesible y coherente con la identidad institucional. Los prototipos validados sirvieron como contrato visual entre usuarios y desarrolladores, reduciendo retrabajo en la fase de construcción.

4.2.1 Actividad 1. Prototipado de la experiencia

Se construyó la estructura de la interfaz tomando como referencia directa el Swagger oficial de MIPRES. A partir de esa guía se maquetaron pantallas en herramientas ligeras y se definió la secuencia de formularios para autenticación, solicitud de token, entrega, reporte y facturación, más la descarga del reporte diario (Ver Anexo E).

4.2.2 Actividad 2. Arquitectura de componentes y lineamientos UI

Se definió una biblioteca de componentes React y se documentaron estados, interacciones y reglas de accesibilidad. Los estilos centralizados en App.css y la guía de microcopys aseguran consistencia visual y reducen la curva de aprendizaje (Ver Anexo F).

4.2.3 Actividad 3. Validación de usabilidad y ajustes

Se realizaron pruebas de usabilidad con la muestra piloto utilizando facturas de montos bajos que podían anularse en caso de error. Las respuestas HTTP devueltas por MIPRES se aprovecharon para guiar correcciones y reducir riesgos. El ejercicio permitió introducir mejoras como autocompletar datos compartidos, resaltar campos obligatorios y alertar sobre posibles envíos incorrectos (Ver Anexo H).

Los artefactos y ajustes obtenidos materializan el Objetivo específico 2.

4.3 Objetivo específico 3: Implementar la lógica de transformación y automatizar los envíos

La solución combina un frontend React/Vite y un backend NestJS que actúa como orquestador seguro frente a la API MIPRES, garantizando manejo de tokens, validaciones consistentes, auditoría y exportación de evidencia.

4.3.1 Actividad 1. Desarrollo del backend

El backend se desarrolló con NestJS, un framework de Node.js que facilita la construcción de aplicaciones eficientes y escalables. Se implementó un módulo de autenticación (AuthModule) que genera y valida tokens JWT (JSON Web Tokens) con una vigencia de 24 horas, garantizando que solo usuarios autorizados puedan acceder a la API. El módulo principal de la aplicación (MipresModule) encapsula la lógica de negocio para interactuar con la API de MIPRES. Este módulo utiliza DTOs (Data Transfer Objects) para validar y estructurar los datos de entrada, asegurando que la información enviada a MIPRES cumpla con el formato esperado. Además, se habilitó CORS (Cross-Origin Resource Sharing) para permitir que el frontend se comunique con el backend, se estableció un prefijo global /api para todas las rutas, y se configuró un limitador de peticiones (ThrottlerModule) para prevenir ataques de fuerza bruta. Toda la comunicación con la API de MIPRES se realiza a través del HttpService de NestJS, y se implementó un sistema de logs estructurados para facilitar la auditoría y el seguimiento de las operaciones (Ver Anexo F).

4.3.2 Actividad 2. Desarrollo del frontend

El frontend se construyó con React y Vite, una combinación que ofrece un entorno de desarrollo rápido y eficiente. La aplicación es una SPA (Single Page Application) que gestiona su estado mediante hooks de React, como useState, useEffect y useCallback. La sesión del usuario y el token de MIPRES se persisten en el localStorage del navegador, permitiendo que la sesión se mantenga activa entre visitas. Los formularios son controlados, lo que significa que el estado de cada campo de entrada está vinculado al estado de un componente de React, facilitando la validación en tiempo real. La aplicación muestra respuestas estructuradas de la API en un formato legible para el usuario y permite descargar un reporte diario en formato JSON con los resultados de las operaciones del día (Ver Anexo I).

4.3.3 Actividad 3. Integración y trazabilidad

Se implementó una bitácora local en el frontend que almacena en el localStorage el cuerpo de cada petición, la respuesta de la API, el código de estado HTTP, la hora y el identificador de la operación. Adicionalmente, el backend registra logs en formato JSON con detalles técnicos de cada solicitud, lo que permite reconstruir incidentes y alimentar métricas de productividad. Esta doble capa de registro (frontend y backend) garantiza una trazabilidad completa de cada operación, desde que el usuario la inicia hasta que se recibe la respuesta de MIPRES (Ver Anexo H).

4.3.4 Actividad 4. Pruebas y estabilización

Se documentaron seis casos de prueba representativos, apoyados en el reporte JSON que genera la plataforma con todas las respuestas de MIPRES. Los escenarios cubrieron cargas exitosas, validaciones fallidas y errores de comunicación, alcanzando un 100 % de cumplimiento tras corregir las incidencias detectadas. Las pruebas de anulación, documentadas en el Anexo H, fueron cruciales para validar el manejo de errores y la correcta interacción con la API de MIPRES.

Como resultado directo de esta automatización, el piloto con el equipo de facturación redujo el tiempo promedio de cargue de un caso de 18 a 7 minutos (61 %), disminuyó la tasa de devoluciones del 21 % al 4 % y elevó la satisfacción percibida de 2,3 a 4,2 puntos sobre 5, cumpliendo el Objetivo 3.

5 Conclusiones

  • La integración de la API MIPRES mediante un backend intermedio y una interfaz guiada redujo barreras técnicas, mejoró tiempos de atención y disminuyó errores de digitación.
  • El enfoque de diseño centrado en el usuario, acompañado de validaciones automáticas e instrumentación de métricas, fortaleció la adopción y generó evidencia cuantitativa del impacto.
  • La arquitectura propuesta es extensible y permite incorporar nuevos catálogos o integraciones con mínimos cambios, habilitando la escalabilidad a otros procesos administrativos.
  • La documentación producida asegura continuidad operativa y facilita la transferencia de conocimiento hacia nuevos integrantes del equipo.

6 Recomendaciones

  1. Automatizar la actualización de catálogos EPS/CUM/CUFE mediante tareas programadas que consuman fuentes oficiales y notifiquen cambios al equipo de facturación.
  2. Integrar un módulo de analítica que visualice en tiempo real los indicadores de desempeño para facilitar decisiones operativas.
  3. Implementar autenticación delegada contra el directorio corporativo para eliminar credenciales locales y reforzar la trazabilidad por usuario.
  4. Extender el piloto a otras sedes o servicios de la clínica incorporando nuevas pruebas de usabilidad y ajustando formularios según particularidades del proceso.
